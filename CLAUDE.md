# UserIdentity

.NET 10 auth service on PolyzenKit, EF Core 10 (Npgsql PostgreSQL provider, snake_case names) and NATS JetStream.

## Layout
- `Application/Core/<Feature>/{Commands,Queries,ViewModels,Shared}`. Handlers implement PolyzenKit interfaces such as `ICreateItemCommandHandler<,>`, `IUpdateItemCommandHandler<,>` or `IGetItemQueryHandler<,>`. Handlers and repositories are registered by name scan. `Shared/` classes (`AppRoleNames`, `UserMessages`, `CleanupBatch`, `TwoFactorRequirement`, `UserChangeAccess`, ...) aren't registered: handlers use them statically. Steps several handlers share are injected handlers (`SignInUserCommandHandler`, `SendLoginCodeCommandHandler`, `RecordFailedSignInCommandHandler`, `GetSecondStepTicketQueryHandler`, `GetSignInSettingsQueryHandler`). Tokens are issued by the command handlers in `Tokens/Commands` (`CreateAccessTokenCommandHandler`, `StartSessionCommandHandler`, `ExchangeRefreshTokenCommandHandler`).
- `Domain/<Table>` holds entities, their `<Table>Limits` classes and their DTO projections, which derive from the entity and set the audit fields inline; response-only DTOs go in the feature's `ViewModels`, and external API shapes in `Infrastructure`. Entities apply their limits with `[MaxLength]`, and configurations store enums with `HasConversion<string>()`. Identity's tables have no entity of ours, so `UserLimits` covers `users` and `user_details`, and `IdentityUserConfiguration` and `IdentityRoleConfiguration` apply the limits to Identity's columns.
- `Common/Enums` holds the enums (sign-in steps, two-factor methods, code outcomes, account limit kinds, message data values), `Common/Errors/ErrorMessages` every error text a client sees, `Common/Identity/UserTokenNames` the names Identity's user store gives the authenticator key and recovery codes, and `Common/Validation/ValidationPatterns` the email format that sign-up, invites and the wait list share, the default role's format, and the scope actions a role claim accepts.
- The service's settings are sealed classes with init-only properties. Each sits next to what reads it: the `Shared/` folder of its feature, and `PasswordHashingSettings` beside `PasswordHashingFilter`. They carry their own rules, as annotations (`[Range]`, `[Url]`) or `IValidatableObject`. `Program.cs` and `Extensions.cs` bind them with PolyzenKit's `AddAppSetting<T>()`, which checks those rules and registers `IOptions<T>`; `PasswordHashingSettings` is only read, with `GetRequiredSetting<T>()`, to build the limiter.
- `Presentation/Endpoints` holds one static class per group (`UserEndpoints`, `RoleEndpoints`, `SignInSettingsEndpoints`, ...), each mapping `MapApiGroup("<Name>")`, which gives the route, the tag and the scope entity. Each endpoint is one `internal static` method that fills the fields the server sets and calls one handler. `AdminApp.GetAsync` resolves the app an admin endpoint works on: the token's app, or the `X-App-Name` app for a global admin. `AdminApp.GetName` gives the role and user endpoints the token's app name, or null for a global admin. `RequestContextReader` reads the client's address (after the forwarded headers) and `User-Agent` for the messages.
- Register, resend-code, reset-password and the wait list sign-up call PolyzenKit's `RequireCaptcha` with their action (`register`, `resend-code`, `reset-password`, `wait-list`), before `PasswordHashingFilter`, so a request waiting on Turnstile holds no hashing place.
- `PasswordHashingFilter` limits concurrent password hashes on the endpoints that hash or check a password. It's an endpoint filter because ASP.NET runs a global rate limiter before the per-IP policy, so requests over their own budget would take queue places from other clients.
- DbContexts are pooled, so `AppDbContext` holds no per-request state. It turns off EF's automatic savepoints, because every handler with a transaction rolls all of it back on failure. A handler that catches a failed save and carries on would need them.
- `Persistence/Repositories/Roles` reads Identity's roles, user roles and role claims in single queries (`IdentityRole` isn't a `BaseEntity`, so `RoleRepository` implements its interface directly).
- `Persistence/Repositories/Users/ProtectedUserStore` subclasses the `UserStore` that Identity's EF stores register and encrypts the authenticator key and recovery codes with PolyzenKit's `IAppSecretProtector`. `Program.cs` registers it as `IUserStore<IdentityUser>` after `AddAppIdentity`.
- `UnitTests/Architecture/LayerDependencyTests` enforces which layer may use which. Fix the code rather than loosening it.
- `AddAppCleanups` registers PolyzenKit periodic deletes for expired refresh tokens, login tickets, password resets and pending email changes, account limit events older than a day, and unconfirmed users (`CleanupSettings`). They work in batches of `CleanupBatch.Size` (100), and the expiry cleanups delete with `ExecuteDeleteAsync`. The unconfirmed-user cleanup takes only users whose every app requires confirmed accounts in its sign-in settings (`UserRepository.GetUnconfirmedEntityItemsCreatedBeforeAsync`; an app without a settings row doesn't); it frees the invite of the user's own app and deletes the Identity user, and foreign keys with cascading deletes remove the details, app links, refresh tokens, tickets, resets, email changes and account limit events. Nothing is soft-deleted, so queries don't filter on `IsDeleted`.

## Sign-in
- Every endpoint that can end in a session goes through `SignInUserCommandHandler`, which applies the step table (`Session`, `ConfirmEmail`, `SecondFactor`, `SetUpSecondFactor`) from the account, the app's sign-in settings and the command's `EmailProven`, `SecondFactorPassed` and `ChangingMethod`. It creates the next ticket, sends `LoginCode`s, marks a proved email confirmed, and is the only place that resets the failure count (when it starts a session).
- `login_tickets` rows are good for one step: each holds its step, the code it waits for (`CodeAction`, `CodeCorrelationId`), `EmailProven`, `ChangingMethod` (a profile's change of method, which continues to setup after the email proof), and the method and phone being set up. `CreateLoginTicketCommandHandler` gives the sign-up's `WelcomeUser` ticket `LoginTicketSettings` and every other ticket `TwoFactorSettings:TicketLifetimeSeconds`.
- Codes are checked and resent through `ICodeCheckService` (`Infrastructure/ExternalServices/CodeCheckService`, built like PolyzenKit's external services: `BaseExternalService`, `IHttpRequestSender`, a service token scoped `<CodeCheckSettings:ServiceName>-message:create`, URLs from `CodeCheckSettings`, the `CodeCheck` entry of `ExternalServicesSettings` for timeout and API key). Anything but 200 with a known outcome throws. `CodeOutcomes.EnsureVerified` turns every other outcome into the one failed-code message, and unknown tickets, resets and email changes still make a check with a random correlation id.
- Two-step sign-in uses `UserManager` for the authenticator and recovery codes. Wrong second-step codes (and emailed or texted ones the code service answers `WrongCode`) go through `RecordFailedSignInCommandHandler`, which counts toward Identity's lockout and the daily `FailedSecondStep` cap. `account_limit_events` hold the daily caps (`AccountLimitSettings`); `GetAccountLimitQueryHandler` decides whether a cap is reached, and `CreateAccountLimitEventCommandHandler` records an event only below it.
- `TwoFactorRequirement` decides whether two-step sign-in is required for an account, and `AllowedTwoFactorMethods` which methods count; a method the app no longer allows counts as none.

## Messaging
- Handlers add `UserMessages` to PolyzenKit's outbox (`ICreateItemCommandHandler<CreateOutboxMessageCommand, OutboxMessageViewModel>`) before their save or commit, one subject per event type: `user.registered` (`WelcomeUser`), `password-reset.requested` (`PasswordReset`), `login-code.requested` (`LoginCode`), `password.changed` (`PasswordChanged`), `sign-up.attempted` (`SignUpAttempted`), `two-factor.changed` (`TwoFactorChanged`) and `contact.changed` (`ContactChanged`), all under `useridentity.`. Notices use a new `Guid.CreateVersion7()` as correlation id; staff changes carry no request context.
- UserIdentity only publishes: it has no `IMessageHandler` and no `MessagingSettings:Subscriptions`.

## Apps and roles
- Sign-in rules live in UserIdentity's `app_sign_in_settings` table, one row per app (`GET`/`PUT /api/v1/sign-in-settings`, global admins, app from `X-App-Name`). `GetSignInSettingsQueryHandler` returns the defaults (every switch off, no default role) for an app without a row. `RequireConfirmedAccount` decides whether an account must prove its email before a session (`AccountConfirmation.IsConfirmed(settings, user)`), sign-up grants `DefaultRole` (`AppRoleNames.DefaultRole`, none while it's null), and the two-factor switches feed `TwoFactorRequirement` and `AllowedTwoFactorMethods`. Apps aren't seeded from configuration; global admins create them through `registered-app`.
- `register-for-service` takes requests signed by one of the app's backends (`AuthorizationPolicies.AppBackend`), takes the app from `ApiRequest.AuthorizedParty`, publishes nothing and answers the user; its audit user is `KnownUsers.SystemId`.
- `Program.cs` calls `AppBootstrapAdminAsync` after migrating and re-encrypting app secrets. `BootstrapAdminCommandHandler` creates the first admin from `BootstrapAdminSettings` (all six or none) only while no user holds the global admin role: it reuses or registers the app (no secret, no sign-in settings row), creates the confirmed account and grants the global admin role and `<app>:admin`. A taken user name or email fails startup, so a signed-up account is never promoted.
- Roles are shared by all apps and named `<app>:<role>`, so admin endpoints are scoped in the handlers. Endpoints pass `AppName` (`AdminApp.GetName`), and handlers use `AppRoleNames` for role names (`AppRoleNames.GetAppRoleAsync` finds a role of the caller's app) and `IUserRegisteredAppRepository.IsUserRegisteredForAppAsync` for users, returning 404 for another app's records. Null means a global admin (`RoleSettings:GlobalAdminRole`). Registered apps are global admin only. Role names are stored in lower case on create and rename.
- `UserChangeAccess` decides who may change whom (user details and two-factor resets): 404 for an account of another app, or for an account holding an admin role (`AppRoleNames.HoldsAdminRole`) when the caller is an app admin and not that user.
- App admins manage their own app's role scopes. Scope strings don't name an app, so this is safe only because tokens carry only `ForApp` roles; every scope-protected endpoint must act only on the caller's app, or also require a role app admins can't give. `CreateRoleClaimCommandHandler` refuses scopes on the global admin role (it's in every app's tokens) and lowercases resource and action, since scopes are compared case-sensitively against lowercase names; `DeleteRoleClaimCommandHandler` lowercases them too.
- Login and reset look up the user name before the email, so `RegisterUserInput` lets a user name look like an email only when it matches the sign-up's own `UserEmail`. A blank `UserEmail` or `PhoneNumber` is stored as null, since `users.normalized_email` is unique. An email change also changes a user name that was the old email (`UserEmailUpdate`).
- Accounts belong to the apps in `user_registered_apps`. `IUserRepository.GetUserDtoAsync` with an app name returns `null` for other apps' users, which is what makes login fail. `CreateAccessTokenCommandHandler` puts only `AppRoleNames.ForApp` roles and their scopes in login, sign-up and refresh tokens.
- Invite codes and wait list entries are keyed by `(AppId, UserEmail)`, and their endpoints resolve the admin's app with `AdminApp.GetAsync`. Invite lists filter by email (up to 100 characters) and applied status before counting and paging.
- An invite's optional `Role` is granted on sign-up, after the app's default role (if any) and in the same transaction. `CreateInviteCodeCommandHandler` accepts only an existing `ForApp` role that isn't an admin role (`AppRoleNames.IsAppAdminRole`, which counts `<app>:admin` as well as `RoleSettings:AdminRoles`), since app admins create invites and must not hand out admin. `RegisterUserCommandHandler` checks the invite whenever `InviteCode` is sent, not only when the app requires one, and answers a missing, wrong or used invite the same way. Only unused invites can be revoked.
- `PasswordResetSettings:MaxRequestsPerDay` counts the last `PasswordResetLimits.RequestCountWindow` of requests, so expired requests are deleted only that long after they expire.
- `users.normalized_email` is unique (`IdentityUserConfiguration`), and `UniqueViolationInterceptor` turns a race into a 400. `RefreshTokenEntity.Version` is a concurrency token, so the second of two simultaneous refreshes gets a 409.

## Commands
- Add a migration: run `dotnet ef migrations add <Name> --project UserIdentity/UserIdentity.csproj --output-dir Persistence/Migrations`. The tool builds the context with `Persistence/AppDbContextFactory`, which reads `DatabaseSettings` from `appsettings.json` and environment variables and applies the same options as the app (`UseAppPostgreSql`). It needs no database and no keys.
- When adding or changing endpoints, update `Readme.md`, and `UserIdentity/UserIdentity.http` when the endpoint is one of its flows. It holds only the main flows and uses only syntax that both Visual Studio and VS Code's REST Client support: file variables, `# @name` with `{{name.response.body.$...}}`, and `{{$timestamp}}` for unique names.

## Tests
- Tests use FakeItEasy, not Moq.
- Endpoint unit tests (`UnitTests/Presentation/Endpoints`) call the endpoint methods directly with faked handlers and an `ApiRequest` from `TestUtils/ApiRequestFactory`, which sets the claims, headers, `RoleSettings` and the group's `ScopeEntityMetadata`. The HTTP integration tests live under `IntegrationTests/Presentation/Endpoints`.
- `TestingWebAppFactory` starts PostgreSQL and NATS, replaces the captcha check with `TestUtils/StubCaptchaVerifier` (which records each check and passes unless a test sets `Passes` to false; `BaseIntegrationTests` resets it before each test), turns rate limiting off, and points `CodeCheckSettings` at `TestUtils/StubHttpServer`, which `TestUtils/CodeCheckStub` answers. Before the host starts it creates UserIdentity's stream (`NatsTestHelper`). Once the host starts, it creates `TestApp`, with a test backend (`TestUtils/TestBackend`, which signs requests with its Ed25519 key), and a second app, `OtherApp`, for cross-app checks (`AppScopingTests`), through PolyzenKit's `CreateRegisteredAppCommand` handler, and gives both sign-in settings that require confirmed accounts with the default role `user`; `BaseIntegrationTests` restores them before each test. Respawn keeps `registered_apps`, `registered_app_backends` and `app_sign_in_settings`, so an app a test creates stays for later tests. `StubHttpServer` is a local Kestrel server: tests set a response per path with `OnPost`, read what arrived from `Requests`, and clear both with `Reset`; anything else gets a 404. `TestDbHelper.CreateUserEntity` also links the user to `TestApp`. `TestUtils/TotpCodes` works out authenticator codes from a setup key.
- `SqlCommandCounter` counts each request's SQL commands by its `X-Request-Id`.
- `TestingWebAppFactory` builds one Respawner, and `BaseIntegrationTests` resets the database with it before each test, roles included, then adds `TestApp`'s admin role back. It must ignore `__EFMigrationsHistory`, or a second host re-runs every migration.
- Other tests' messages share the stream, so `NatsTestHelper` reads it with an ordered consumer and filters by correlation id or by a predicate; notices have new correlation ids, so tests find them by recipient.
- Compare JSON values as text (`$"{jsonObject["error"]?["message"]}"`): `Assert.Equal(string, JToken)` passes for any value.
- `InviteOpenApiContractTests` exports the Development contract from a disposable InMemory host, with no broker or database.
- `UserIdentity.SmokeTests` runs the published image with no reference to the service. Its bootstrap admin creates `testapp`, then turns on confirmed accounts and the default role through `PUT /api/v1/sign-in-settings`, and the code check goes to a stub reached through `CodeCheckSettings__VerifyUrl` and `__ResendUrl`. Kestrel limits can only be tested there, because TestServer doesn't enforce them. A request-size test must send every required field, or it stops at validation and shows nothing.
